# ContestFlow 数模协作

团队决定题意、模型假设、路线、预算和最终结论；Agent 在已经授权的阶段内辅助执行；ContestFlow CLI 保存证据并检查已实现的技术约束。CLI 不调用模型，不提供后台 Agent 或比赛平台上传。

## 定位当前任务

1. 先辨认用户要处理的比赛工作区和本阶段目标。包含 `contest.json` 的目录才是比赛工作区；用绝对路径运行 `contestflow repo WS`，`local` / `team` 模式须确认 `status: ready`、`root_matches: true` 且仓库顶层就是 `WS`。不得依据当前终端或工具包源码位置猜测。已有工作区读取 `AGENTS.md`、`docs/DECISIONS.md`、`docs/AI_TASK.md`，使用 `status` / `next` 核对产物状态；目录中存在 `deliverables/FROZEN.json` 时保持冻结文件只读。
2. 定位安装了 `contestflow-local` 的 Python 环境，优先使用用户指定环境或项目已有虚拟环境。用该环境的 `python -m contestflow --version` 核对可用性；CLI 不在 PATH 时继续使用该解释器或虚拟环境中命令的绝对路径。skill 目录不等于工具源码目录，也不等于比赛工作区。
3. 软件未安装、首次准备比赛或工具路径有问题时，只读下方环境指南。已有环境和授权可沿用；不重复安装或重新初始化已有比赛。
4. 执行当前任务需要的操作，按下方阶段读取对应指南，不一次加载所有参考文件。

| --- | --- |

## 主动推进闭环

- 进入任务先根据目标和证据建立工作计划：优先项、依赖、预算、完成条件、停止条件和需要团队判断的事项。`plan` / `next` 是产物状态提示，不替代 Agent 的具体计划，也不表示团队批准。
- 按“规划 → 执行 → 验证 → 复盘 → 继续”工作。选择价值最高且不受阻的事项连续完成，不停在列计划、给建议或报告状态；已有授权内的普通实现、实验、修复和整理不逐条询问。
- 每个有意义阶段更新 `docs/DECISIONS.md`：完成项、证据、失败、局限、当前阶段和下一步；实质性 AI 参与同步到 `docs/AI_USAGE.md`。随后刷新 `plan`，仍在范围内且未受阻就继续。
- 只有缺少会改变路线、指标或预算的团队判断，涉及付费、账户、不可逆操作、外部提交，或工作区冻结时暂停。暂停前完成不依赖该决定的工作并给出有依据的选项。用户只要求窄范围任务时，以该范围为边界。
- 新题先形成读题包并做不依赖路线决定的准备，不臆测团队已经选择模型。自动检查、呈现选择、AI 审读、团队审定和平台成功是不同事实；`human_review: not_asserted` 不因工具成功而改变。

## 调用与失败处理

参考中的 `WS`、`MATERIALS`、`SELECTION.json` 是需替换的路径占位；`contestflow` 指已定位环境中的命令，可改为该环境的 `python -m contestflow`。显式传比赛工作区，算法写在工作区的 `src/`，不误改工具包实现。

先查看所用版本的 `--help`。正常业务结果为 UTF-8 JSON；退出码 `0` 表示命令完成，`1` 表示实验存在未成功记录或预检失败，已处理的配置/文件错误为 `2`。已处理业务错误写 stderr JSON；参数解析错误则是 argparse 文本，不能一律当 JSON。意外崩溃也可能返回其他非零码。

失败时保留原始记录，定位输入、配置、依赖或真实算法问题并修复，随后只重跑受影响环节。不要为了让流程变绿而改哈希、掩盖失败、伪造 `valid` 或放宽题定口径。环境盘点或合成预演成功只说明该检查的能力与范围；任何候选论文或 ZIP 都需团队理解和审定。
